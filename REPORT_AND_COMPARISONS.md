# LowBit Trace Corpus -- Report and Cross-Backend Comparisons

This document is the top-level summary across all five measurement
backends. Each backend's own detailed numbers live in its own folder
(`<backend>/REPORT.md`); this file compares them side-by-side,
deliberately, with the caveats that make such a comparison valid kept
front and center. Read `LIMITATIONS.md` first.

## Backend status at a glance

| Backend | Folder | Real run in this repo? | What it can tell you |
|---|---|---|---|
| QEMU (no perf wrapping) | `qemu/` | **Yes, 500/500 programs** | Correctness + wall-clock timing under RISC-V emulation |
| gem5, `MinorCPU` | `gem5/` | **Yes, 500/500 programs** | Simulated branch-predictor + cache-hierarchy behavior |
| gem5, `AtomicSimpleCPU` | `gem5/` | **Yes, 500/500 programs** | Simulated cache/IPC only -- no branch data (see `gem5/REPORT.md`) |
| gem5, `DerivO3CPU` | `gem5/` | No -- known upstream gem5 hang, see `gem5/REPORT.md` | -- |
| Spike (golden-model ISA sim) | `spike/` | **Yes, 500/500 programs** | Correctness + relative instruction-volume timing |
| x86-64 native | `x86-64/` | **Yes, 500/500 programs, real hardware perf** | Real branch/cache counters on real silicon, wrong ISA |
| Orange Pi (real RISC-V HW) | `orange-pi/` | No -- no RISC-V board in this environment | Ground truth: real RISC-V branch/cache behavior |

Four of five backends now have real, complete data. `orange-pi/` is
the single remaining gap -- the only backend that could confirm or
contradict whether the simulated/emulated numbers below track real
RISC-V silicon.

## Finding 1: the benchmark logic is correct and architecture-portable

The strongest result in this corpus isn't a performance number, it's a
**correctness** one. `qemu/lowbit_traces_qemu.csv` and
`x86-64/lowbit_traces_native.csv` were generated by completely
different toolchains (RISC-V cross-compile + `qemu-riscv64` emulation
vs. native `gcc` on real x86-64 silicon), on two different
instruction-set architectures, from the same 500 `.c` sources with the
same fixed seed. Comparing `taken`, `nottaken`, and `sink` across all
500 programs:

```
qemu vs x86-64 taken/nottaken/sink mismatches: 0 / 500
```

Every single program produced bit-identical branch-outcome and
side-effect-sink values on two unrelated execution paths. That's real
evidence the benchmark logic itself -- 50 branch-pattern generators, 50
cache-pattern generators, `lowbit_runtime.h`'s shared LCG and timing
harness -- is deterministic and correct, not an artifact of either
backend's specific behavior.

A second, independent check: `spike/lowbit_traces_spike.csv` (built
with a completely different compiler, `riscv64-unknown-elf-gcc`/
newlib, and run under a golden-model ISA simulator rather than an
emulator) uses a capped `N=20000` instead of each program's full-scale
`N`, so exact totals can't match -- but the `taken/N` *ratio* should be
roughly N-invariant for most branch patterns. It matches `qemu/`'s
ratio within 2% for **441/500 programs (88.2%)**. The remaining 11.8%
aren't a correctness concern: they cluster almost entirely around
branch families with an explicit warmup/phase-transition component
(`b26_warmup_then_steady`, `b13_single_phase_change`,
`b22_drifting_threshold_periodic_reset`) whose taken-ratio is *supposed*
to shift with N by design, since a fixed-length warmup phase becomes a
smaller fraction of a larger N. Three independent execution paths,
two different compilers, two different ISAs, all agreeing on
correctness.

## Finding 2: three backends agree on the hardest cache patterns

`c10_pointer_chase_linked_list` and `c32_hilbert_curve_traversal` are
the two slowest cache-pattern families by wall-clock time on **both**
`qemu/` and `x86-64/` (completely different ISAs), and
`c10_pointer_chase_linked_list` is also one of the two hardest by
*simulated cache-miss rate* under `gem5/`'s `MinorCPU` (a genuinely
different metric on a genuinely different execution model). `spike/`'s
instruction-volume proxy for `c32_hilbert_curve_traversal` agrees too,
for the mechanistically obvious reason that Hilbert-curve index
computation requires more instructions per access step regardless of
what's measuring it.

| Backend | Metric | 2 hardest cache families |
|---|---|---|
| `qemu/` | wall-clock roi | `c10_pointer_chase_linked_list`, `c32_hilbert_curve_traversal` |
| `x86-64/` | wall-clock roi | `c10_pointer_chase_linked_list`, `c32_hilbert_curve_traversal` |
| `gem5/` `MinorCPU` | simulated cache-miss rate | `c10_pointer_chase_linked_list`, `c33_cache_set_conflict_stress` |
| `spike/` | instruction-volume proxy | `c32_hilbert_curve_traversal`, `c42_cache_oblivious_funnel_stride` |

Four backends, four different measurement mechanisms (host wall-clock
under emulation, real hardware wall-clock, simulated cache-hierarchy
miss rate, functional-simulator instruction count), landing on
overlapping answers. Pointer chasing defeating hardware prefetch, and
Hilbert-curve traversal requiring extra per-step computation, are real
properties of those access patterns -- not an artifact of any one
backend's implementation.

## Finding 3: two backends agree on the hardest and easiest branch patterns

`x86-64/`'s real hardware branch-predictor counters and `gem5/`'s
simulated `MinorCPU` branch predictor independently agree on both ends
of the difficulty spectrum:

| Rank | `x86-64/` (real hardware) | `gem5/` `MinorCPU` (simulated) |
|---|---|---|
| Easiest | `b08_switch_multiway`, `b07_nested_dependent`, `b03_alternating` | `b08_switch_multiway`, `b10_correlated_history`, `b05_periodic8_biased` |
| Hardest | `b06_pseudo_random_50`, `b23_popcount_parity`, `b30_periodic_interrupt_override` | `b06_pseudo_random_50`, `b23_popcount_parity`, `b30_periodic_interrupt_override` |

The three hardest branch families are **identical, in the same
relative order**, on real Intel silicon and a simulated in-order
RISC-V core. `b08_switch_multiway` (a dispatch table with locally
repetitive control flow) tops the easy list on both. This is exactly
the shape you'd want from benchmark patterns explicitly designed to
probe predictor behavior -- real, cross-architecture agreement, not
coincidence.

`spike/`'s branch-family ranking looks different (`b47_mutual_ping_pong_recursion`,
`b09_recursive_calls` hardest) -- and that's expected, not a
disagreement: spike has no branch predictor to mispredict at all, so
what it measures there is raw control-flow/instruction overhead
(recursive call cost), a genuinely different question from
predictability. See `spike/REPORT.md` for the full explanation.

## Finding 4: AtomicSimpleCPU cannot answer branch-prediction questions

Worth stating plainly since it's an easy mistake to make from the raw
CSV alone: `gem5/lowbit_traces_gem5_atomcpu.csv` has
`branches_total=0` and `branch_misses_total=0` for all 500 rows, with
`unmatched_metrics=branches_total;branch_misses_total` flagging every
single one. `AtomicSimpleCPU` has no branch-predictor unit at all (it's
a functional, fixed-latency-per-instruction model) -- those zeros mean
**not measured**, not **0% miss rate**. Use `gem5/`'s `MinorCPU` data,
not `AtomicSimpleCPU`, for anything involving branch behavior;
`AtomicSimpleCPU`'s cache/IPC data is still real and usable (see
`gem5/REPORT.md`).

## Finding 5: qemu's redesign removed a real correctness bug, not just a documentation gap

Worth recording here since it affects how much to trust re-runs of
this corpus against future changes: `qemu/`'s script briefly went
through a version that tried to collect *exact guest instruction
counts* via `qemu-riscv64 -singlestep -d exec`. It had two compounding
bugs (a size-cap heuristic that could never trigger, and a
`-d exec` flag that silently produces no output on stock, non-debug
QEMU builds) that together meant **every one of the 500 programs
either ran impractically slowly or returned a CSV with essentially no
real data** -- blank `validation`, blank `arch`, blank `compiler`,
`perf_available=0` across the board. That version's output would have
looked superficially like "500 rows, so it ran" to anyone not checking
column contents. The fix removed the broken feature entirely rather
than patching around it, and re-validated end-to-end (the `taken`/
`nottaken`/`sink` cross-check against `x86-64/` in Finding 1 above is
from the corrected script). If you're auditing this corpus's history
or reusing an old CSV, check `qemu/REPORT.md`'s "read this before
anything else" note first.

## What real orange-pi data would add

Every finding above rests on emulation (`qemu/`), simulation
(`gem5/`), a golden-model ISA simulator (`spike/`), or real silicon of
the *wrong* ISA (`x86-64/`). None of them can independently confirm
whether `gem5/`'s specific `MinorCPU`/`AtomicSimpleCPU` configurations
-- one particular branch predictor, one particular cache geometry --
actually track real RISC-V hardware behavior, or whether they happen
to agree with `x86-64/`'s findings (Finding 3) for reasons that
wouldn't hold on real RISC-V silicon. Running `orange-pi/` and
repeating Findings 2 and 3 with real RISC-V hardware data in the
comparison table is the single most valuable next step for this
corpus; see `orange-pi/REPORT.md` for exactly what to check once
that's run.
